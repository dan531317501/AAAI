我们如何构建多 Agent 研究系统

已发表 2025年6月13日

我们的研究功能使用多个 Claude Agent 来更有效地探索复杂的主题。我们分享工程挑战以及我们从构建该系统中学到的经验教训。

Claude 现在有 研究能力 允许它在网络、Google Workspace 和任何集成中进行搜索以完成复杂的任务。

这个多 Agent 系统从原型到生产的历程给我们带来了有关系统架构、工具设计和 prompt 工程的重要教训。多 Agent 系统由多个一起工作的 Agent（LLM 在循环中自主使用工具）组成。我们的研究功能涉及 Agent，它根据用户查询规划研究过程，然后使用工具创建同时搜索信息的并行 Agent。具有多个 Agent 的系统在 Agent 协调、评测 和可靠性方面引入了新的挑战。

这篇文章详细介绍了对我们有用的原则——我们希望您会发现它们在构建您自己的多 Agent 系统时很有用。

多 Agent 系统的优点

研究工作涉及开放式问题，很难提前预测所需的步骤。您无法硬编码固定路径来探索复杂的主题，因为该过程本质上是动态的且依赖于路径。当人们进行研究时，他们倾向于根据调查结果不断更新他们的方法，遵循调查过程中出现的线索。

这种不可预测性使得 AI Agent 特别适合研究任务。研究需要随着调查的展开而灵活地调整或探索切线联系。该模型必须自主运行多次，根据中间结果决定要追求的方向。线性的一次性管道无法处理这些任务。

搜索的本质是压缩：从庞大的语料库中提取见解。 SubAgent 通过与自己的上下文窗口并行操作来促进压缩，在为领先研究 Agent 压缩最重要的标记之前同时探索问题的不同方面。每个 subAgent 还提供关注点分离（不同的工具、prompt 和探索轨迹），从而减少路径依赖性并实现彻底、独立的调查。

一旦智能达到阈值，多 Agent 系统就成为扩展性能的重要方式。例如，尽管在过去 10 万年里，人类个体变得更加聪明，但人类社会却变得更加聪明。 指数地 因为我们在信息时代更有能力 集体的 智力和协调能力。即使是一般智力的 Agent 在作为个人运作时也会面临限制； Agent 小组可以完成更多工作。

我们的内部 评测 表明，多 Agent 研究系统尤其适合涉及同时追求多个独立方向的广度优先查询。我们发现，以 Claude Opus 4 为主导的多 Agent 系统 Agent 和 Claude Sonnet 4 subAgent 优于单 Agent Claude Opus 4 在我们的内部研究 eval 上提高了 90.2%。例如，当被要求识别信息技术 S&P 500 中公司的所有董事会成员时，多 Agent 系统通过将其分解为子 Agent 的任务来找到正确的答案，而单个 Agent 系统无法通过缓慢的顺序搜索找到答案。

多 Agent 系统之所以有效，主要是因为它们有助于花费足够的代币来解决问题。在我们的分析中，三个因素解释了 95% 的性能差异 BrowseComp 评测（测试浏览Agent定位难以查找的信息的能力）。我们发现，代币使用本身就解释了 80% 的差异，工具调用次数和模型选择是另外两个解释因素。这一发现验证了我们的架构，该架构通过单独的上下文窗口在 Agent 上分配工作，以增加并行推理的更多能力。最新的 Claude 模型可作为代币使用的巨大效率倍增器，因为升级到 Claude Sonnet 4 的性能增益比 Claude Sonnet 3.7 代币预算加倍更大。多个 Agent 架构可以有效地扩展超出单个 Agent 限制的任务的令牌使用量。

有一个缺点：在实践中，这些架构会快速消耗代币。在我们的数据中，Agent 通常使用比聊天交互多约 4 倍的令牌，而多 Agent 系统使用比聊天多约 15 倍的令牌。为了经济可行性，多 Agent 系统需要任务价值足够高的任务来支付提高的性能。此外，一些要求所有 Agent 共享相同上下文或涉及 Agent 之间的许多依赖关系的域不太适合当今的多 Agent 系统。例如，大多数编码任务涉及的真正可并行任务比研究要少，并且 LLM Agent 还不擅长实时协调和委托给其他 Agent。我们发现，多 Agent 系统擅长执行涉及大量并行化、超出单个上下文窗口的信息以及与众多复杂工具交互的有价值的任务。

研究架构概述

我们的研究系统使用具有协调者-工作者模式的多 Agent 架构，其中领导 Agent 协调流程，同时委托给并行运行的专门 subAgent。

当用户提交查询时，领导者 Agent 会对其进行分析，制定策略，并生成子 Agent 以同时探索不同的方面。如上图所示，子Agent通过迭代地使用搜索工具收集信息来充当智能过滤器，在本例中是2025年的AI Agent公司，然后将公司列表返回给领导者Agent，以便它可以编译最终答案。

使用 Retrieval 增强生成 (RAG) 的传统方法使用静态 retrieval。也就是说，它们获取与输入查询最相似的一组块，并使用这些块来生成响应。相比之下，我们的架构使用多步骤搜索，动态查找相关信息，适应新的发现，并分析结果以制定高质量的答案。

即时工程和 评测 用于研究 Agent

多 Agent 系统与单 Agent 系统具有关键区别，包括协调复杂性的快速增长。早期的 Agent 犯了一些错误，例如为简单查询生成 50 个 subAgent、无休止地在网络上搜索不存在的来源以及通过过多的更新分散彼此的注意力。由于每个 Agent 都由 prompt 操纵，因此 prompt 工程是我们改善这些行为的主要杠杆。以下是我们从 prompting Agent 中学到的一些原理：

  1. 像您的 Agent 一样思考。 要迭代 prompt，您必须了解它们的效果。为了帮助我们做到这一点，我们使用我们的 控制台 使用我们系统中的精确 prompt 和工具，然后观看 Agent 逐步工作。这立即揭示了故障模式：Agent 在已经获得足够结果的情况下继续使用过于冗长的搜索查询或选择不正确的工具。有效的 prompting 依赖于开发 Agent 的准确心理模型，这可以使最有影响力的变化变得显而易见。
  2. 教协调者如何委派。 在我们的系统中，领导 Agent 将查询分解为子任务并将它们描述给 subAgent。每个 subAgent 都需要一个目标、输出格式、使用工具和来源的指南以及明确的任务边界。如果没有详细的任务描述，Agent 会重复工作、留下空白或无法找到必要的信息。我们首先允许领导 Agent 给出简单、简短的指令，例如“研究半导体短缺”，但发现这些指令通常非常模糊，以至于 subAgent 会误解任务或执行与其他 Agent 完全相同的搜索。例如，一个 subAgent 探讨了 2021 年的汽车芯片危机，而另外两个则重复了调查当前 2025 年供应链的工作，没有进行有效的分工。
  3. 扩展查询复杂性的工作量。 Agent很难判断不同任务的适当努力，因此我们在 prompt 中嵌入了缩放规则。简单的事实调查仅需要 1 个 Agent 和 3-10 个工具调用，直接比较可能需要 2-4 个 subAgent，每个 subAgent 10-15 个调用，复杂的研究可能使用 10 个以上的 subAgent ，并且职责划分明确。这些明确的指导方针可以帮助领导者 Agent 有效地分配资源并防止在简单查询上的过度投资，这是我们早期版本中常见的失败模式。
  4. 工具的设计和选择至关重要。 Agent工具接口与人机接口一样重要。使用正确的工具是高效的——通常，这是绝对必要的。例如，Agent 在网络上搜索仅存在于 Slack 中的上下文从一开始就注定要失败。与 MCP 服务器 使模型能够访问外部工具，这个问题变得更加复杂，因为 Agent 遇到了质量差异很大的描述的看不见的工具。我们给出了 Agent 明确的启发：例如，首先检查所有可用的工具，将工具的使用与用户意图相匹配，在网络上搜索广泛的外部探索，或者更喜欢专用工具而不是通用工具。错误的工具描述可能会将 Agent 引向完全错误的路径，因此每个工具都需要有明确的用途和清晰的描述。
  5. 让Agent提升自己。我们发现Claude 4个型号可以成为优秀的prompt工程师。当给定 prompt 和故障模式时，他们能够诊断 Agent 失败的原因并提出改进建议。我们甚至创建了一个工具测试 Agent - 当给出有缺陷的 MCP 工具时，它会尝试使用该工具，然后重写工具描述以避免失败。通过对该工具进行数十次测试，Agent 发现了关键的细微差别和错误。这种改进工具人体工程学的过程使得使用新描述的未来 Agent 的任务完成时间减少了 40%，因为他们能够避免大多数错误。
  6. 从宽范围开始，然后缩小范围。 搜索策略应该反映专家的人类研究：在深入研究细节之前探索景观。Agent通常默认使用过长的特定查询，但返回的结果很少。我们通过 prompting Agent 来抵消这种趋势，从简短、广泛的查询开始，评估 可用的内容，然后逐渐缩小焦点。
  7. 指导思维过程。 扩展思维模式，导致Claude在可见的思维过程中输出额外的代币，可以作为可控的暂存器。领导 Agent 使用思维来规划其方法，评估哪些工具适合任务，确定查询复杂性和 subAgent 计数，并定义每个 subAgent 的角色。我们的测试表明，扩展思维可以改善指令遵循、推理和效率。 SubAgent 也计划好，然后使用 交错思维 在工具结果达到 评估 质量后，找出差距并优化下一个查询。这使得 subAgent 能够更有效地适应任何任务。
  8. 并行工具调用可提高速度和性能。 复杂的研究任务自然涉及探索许多来源。我们早期的 Agent 执行顺序搜索，速度慢得令人痛苦。为了速度，我们引入了两种并行化：（1）主 Agent 并行而不是串行地旋转 3-5 个子 Agent； (2) subAgent 并行使用 3 个以上工具。这些变化将复杂查询的研究时间缩短了 90%，使研究能够在几分钟而不是几小时内完成更多工作，同时覆盖比其他系统更多的信息。

我们的 prompting 策略侧重于灌输良好的启发式方法，而不是严格的规则。我们研究了熟练的人类如何处理研究任务，并将这些策略编码在我们的 prompt 中，这些策略包括将困难的问题分解为更小的任务、仔细地调整来源的质量、根据新信息调整搜索方法，以及识别何时关注深度（详细研究一个主题）与广度（并行探索多个主题）。我们还通过设置显式 guardrail 来防止 Agent 失控，主动减轻意外的副作用。最后，我们专注于具有可观察性和测试用例的快速迭代循环。

Agent 的有效 评测

良好的 评测 对于构建可靠的 AI 应用程序至关重要，Agent 也不例外。然而，评估 多 Agent 系统提出了独特的挑战。传统的 评测 通常假设 AI 每次都遵循相同的步骤：给定输入 X，系统应遵循路径 Y 产生输出 Z。但多 Agent 系统不会以这种方式工作。即使起点相同，Agent 也可能采取完全不同的有效路径来达到目标​​。一个 Agent 可能会搜索三个来源，而另一个 Agent 可能会搜索十个来源，或者他们可能会使用不同的工具来找到相同的答案。因为我们并不总是知道什么是正确的步骤，所以我们通常不能仅仅检查 Agent 是否遵循了我们事先规定的“正确”步骤。相反，我们需要灵活的 评测 方法来判断 Agent 是否达到了正确的结果，同时遵循合理的流程。

立即开始 评估 小样本。在 Agent 开发的早期，变化往往会产生巨大的影响，因为有大量唾手可得的成果。 prompt 调整可能会将成功率从 30% 提高到 80%。由于效果大小如此之大，您只需几个测试用例即可发现变化。我们从一组大约 20 个代表真实使用模式的查询开始。测试这些查询通常可以让我们清楚地看到更改的影响。我们经常听说 AI 开发团队推迟创建 eval，因为他们认为只有具有数百个测试用例的大型 eval 才有用。然而，最好立即从一些示例开始小规模测试，而不是推迟到可以构建更彻底的 eval 为止。

LLM 作为评判 评测 在做得好时会缩放。 研究成果很难以编程方式 评估，因为它们是自由格式的文本，很少有单一的正确答案。 LLM 非常适合对输出进行分级。我们使用 LLM 判断，评估 根据标题中的标准对每个输出进行评估：事实准确性（声明是否与来源匹配？）、引用准确性（引用的来源是否与声明匹配？）、完整性（是否涵盖了所有要求的方面？）、来源质量（是否使用了主要来源而不是较低质量的二手来源？）以及工具效率（是否使用了正确的工具合理的次数？）。我们用多个评判者对 评估 每个组件进行了实验，但发现单个 LLM 调用与单个 prompt 输出 0.0-1.0 的分数以及通过/不及格等级是最一致且与人类判断一致的。当 eval 测试用例时，此方法特别有效 做了 有了明确的答案，我们可以使用 LLM 判断来简单检查答案是否正确（即是否准确列出了研发预算排名前 3 名的制药公司？）。使用 LLM 作为判断器使我们能够扩展 评估 数百个输出。

人类 评测 能够捕捉到自动化遗漏的内容。 测试 Agent 的人员会发现 eval 遗漏的边缘情况。其中包括对异常查询、系统故障或微妙的源选择偏差的幻觉答案。在我们的案例中，人类测试人员注意到，我们早期的 Agent 始终选择 SEO- 优化的内容农场，而不是权威但排名较低的来源，例如学术 PDF 或个人博客。将源质量启发式添加到我们的 prompt 有助于解决此问题。即使在自动化的世界中，手动测试仍然至关重要。

多 Agent 系统具有紧急行为，无需特定编程即可出现。例如，对前导 Agent 的微小更改可能会不可预测地改变 subAgent 的行为方式。成功需要理解交互模式，而不仅仅是个人 Agent 行为。因此，对于这些Agent来说，最好的prompt不仅仅是严格的指示，而是定义分工、解决问题的方法和工作预算的协作框架。做到这一点依赖于仔细的 prompting 和工具设计、可靠的启发式、可观察性和紧密的反馈循环。 请参阅 我们的 Cookbook 中的开源 prompt 例如我们系统中的 prompt。

生产可靠性和工程挑战

在传统软件中，错误可能会破坏功能、降低性能或导致中断。在 Agent 系统中，微小的变化会级联成大的行为变化，这使得为必须在长时间运行的进程中维护状态的复杂 Agent 编写代码变得非常困难。

Agent是有状态的并且错误是复合的。 Agent可以长时间运行，在许多工具调用中维护状态。这意味着我们需要持久地执行代码并处理错误。如果没有有效的缓解措施，轻微的系统故障对于 Agent 来说可能是灾难性的。当错误发生时，我们不能从头开始：重新启动的成本很高，而且会让用户感到沮丧。相反，我们构建了可以从发生错误时 Agent 所在位置恢复的系统。我们还利用模型的智能来优雅地处理问题：例如，让 Agent 知道工具何时出现故障并让它适应，效果出奇地好。我们将基于 Claude 的 AI Agent 的适应性与重试逻辑和定期检查点等确定性保护措施相结合。

调试受益于新方法。 即使使用相同的 prompt，Agent也会做出动态决策，并且在运行之间是不确定的。这使得调试更加困难。例如，用户会报告 Agent“没有找到明显的信息”，但我们不明白为什么。 Agent 是否使用了错误的搜索查询？选择不良来源？打击工具故障？通过添加完整的生产跟踪，我们可以诊断 Agent 失败的原因并系统地解决问题。除了标准的可观察性之外，我们还监控 Agent 决策模式和交互结构 - 所有这些都无需监控个人对话的内容，以维护用户隐私。这种高级可观察性帮助我们诊断根本原因、发现意外行为并修复常见故障。

部署需要仔细协调。 Agent系统是由 prompt、工具和执行逻辑组成的高度状态网络，几乎连续运行。这意味着每当我们部署更新时，Agent 可能位于其进程中的任何位置。因此，我们需要防止善意的代码更改破坏现有的 Agent。我们无法同时将每个 Agent 更新到新版本。相反，我们使用 彩虹部署 为了避免中断 Agent 的运行，请逐渐将流量从旧版本转移到新版本，同时保持两个版本同时运行。

同步执行会产生瓶颈。 目前，我们的lead Agent同步执行subAgent，等待每组subAgent完成后再继续。这简化了协调，但在 Agent 之间的信息流中造成了瓶颈。例如，领导者Agent无法引导subAgent，subAgent无法协调，并且在等待单个subAgent完成搜索时整个系统可能会被阻塞。异步执行将启用额外的并行性：Agent 并发工作并在需要时创建新的 subAgent。但这种异步性增加了结果协调、状态一致性和跨 subAgent 的错误传播的挑战。由于模型可以处理更长、更复杂的研究任务，我们预计性能的提升将证明复杂性的合理性。

结论

当建造 AI Agent 时，最后一英里往往成为旅程的大部分。在开发人员机器上运行的代码库需要大量的工程才能成为可靠​​的生产系统。 Agent 系统中错误的复合性质意味着传统软件的小问题可能会完全破坏 Agent。一步失败可能会导致 Agent 探索完全不同的轨迹，从而导致不可预测的结果。由于本文中描述的所有原因，原型和生产之间的差距通常比预期的要大。

尽管存在这些挑战，事实证明，多 Agent 系统对于开放式研究任务很有价值。用户表示，Claude 帮助他们找到了他们没有考虑过的商机、浏览复杂的医疗保健选项、解决棘手的技术错误，并通过发现他们单独无法找到的研究联系来节省长达数天的工作时间。多 Agent 研究系统可以通过仔细的工程、全面的测试、注重细节的 prompt 和工具设计、稳健的操作实践以及对当前 Agent 功能有深入了解的研究、产品和工程团队之间的紧密合作，实现大规模可靠运行。我们已经看到这些系统改变了人们解决复杂问题的方式。

附录

以下是针对多 Agent 系统的一些其他杂项提示。

Agent 的最终状态 eval 使状态在许多回合中发生突变。 评估在多轮对话中修改持久状态的 Agent 提出了独特的挑战。与只读研究任务不同，每个操作都可以更改后续步骤的环境，从而创建传统 评测 方法难以处理的依赖关系。我们发现成功的重点是最终状态 评测 而不是逐轮分析。 evalu 不是判断 Agent 是否遵循特定过程，而是判断它是否达到了正确的最终状态。这种方法承认 Agent 可以找到实现同一目标的替代路径，同时仍然确保它们提供预期结果。对于复杂的工作流程，将 评测 分解为应该发生特定状态更改的离散检查点，而不是尝试验证每个中间步骤。

长视野对话管理。 生产 Agent 经常进行数百轮对话，需要仔细的上下文管理策略。随着对话的扩展，标准上下文窗口变得不足，需要智能压缩和内存机制。我们实现了 Agent 总结已完成的工作阶段并在继续执行新任务之前将基本信息存储在外部存储器中的模式。当上下文限制接近时，Agent 可以生成具有干净上下文的新子 Agent，同时通过仔细的切换保持连续性。此外，他们可以从记忆中检索存储的上下文（例如研究计划），而不是在达到上下文限制时丢失以前的工作。这种分布式方法可以防止上下文溢出，同时保持扩展交互中对话的连贯性。

SubAgent 输出到文件系统以最小化“电话游戏”。 对于某些类型的结果，直接 subAgent 输出可以绕过主协调器，从而提高保真度和性能。与其要求 subAgent 通过主导 Agent 传达所有内容，不如实施工件系统，其中专门的 Agent 可以创建独立持续的输出。 SubAgent 调用工具将其工作存储在外部系统中，然后将轻量级引用传递回协调器。这可以防止多阶段处理期间的信息丢失，并减少通过对话历史记录复制大量输出的令牌开销。该模式特别适用于代码、报告或数据可视化等结构化输出，其中 subAgent 的专用 prompt 产生比通过通用协调器过滤更好的结果。
