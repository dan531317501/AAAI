面向 AI Agent 的高效上下文工程

已发表 2025年9月29日

对于 AI Agent 来说，上下文是关键但有限的资源。在这篇文章中，我们探讨了有效策划和管理为其提供动力的环境的策略。

prompt 工程成为 AI 应用领域关注的焦点几年后，一个新术语开始引人注目： 情境工程。使用语言模型进行构建不再是为您的 prompt 找到正确的单词和短语，而是更多地回答更广泛的问题：“哪种上下文配置最有可能生成我们模型所需的行为？”

背景 指从大语言模型 (LLM) 采样时包含的标记集。的 工程 当前的问题是根据 LLM 的固有限制优化这些代币的效用，以便始终如一地实现预期结果。有效地争论 LLM 通常需要 结合上下文思考 — 换句话说：考虑 LLM 在任何给定时间可用的整体状态以及该状态可能产生的潜在行为。

在这篇文章中，我们将探索情境工程的新兴艺术，并提供一个用于构建可操纵、有效的 Agent 的精致思维模型。

上下文工程与 prompt 工程

在 Anthropic，我们将上下文工程视为 prompt 工程的自然发展。即时工程是指编写和组织 LLM 指令以获得最佳结果的方法（参见 我们的文档 了解概述和有用的 prompt 工程策略）。 情境工程 指的是在 LLM 推理期间用于策划和维护最佳标记（信息）集的策略集，包括可能落在 prompt 之外的所有其他信息。

在使用 LLM 进行工程的早期，prompting 是 AI 工程工作的最大组成部分，因为日常聊天交互之外的大多数用例都需要针对一次性分类或文本生成任务进行优化的 prompt。顾名思义，prompt工程的主要关注点是如何编写有效的prompt，特别是系统prompt。然而，随着我们朝着设计更强大的 Agent 的目标迈进，该 Agent 可以在多轮推理和更长的时间范围内运行，我们需要管理整个上下文状态的策略（系统指令、工具、 模型上下文协议 （MCP）、外部数据、消息历史记录等）。

循环运行的 Agent 会生成越来越多的数据， 可以 与下一轮推理相关，并且该信息必须循环完善。情境工程是 艺术与科学 从不断变化的可能信息宇宙中策划哪些内容将进入有限的上下文窗口。

为什么上下文工程对于构建有能力的 Agent 很重要

尽管 LLM 的速度和能力能够管理越来越大的数据量，但我们观察到，LLM 和人类一样，在某个时刻会失去注意力或感到困惑。大海捞针的研究 风格基准测试揭示了以下概念： 上下文腐烂：随着上下文窗口中标记数量的增加，模型准确回忆上下文信息的能力会下降。

虽然某些模型比其他模型表现出更温和的退化，但这一特征在所有模型中都存在。因此，背景必须被视为边际收益递减的有限资源。就像人类一样，他们有 工作记忆容量有限，LLM 在解析大量上下文时有一个“注意力预算”。每引入一个新代币都会消耗一定数量的预算，从而增加了仔细策划 LLM 可用代币的需要。

这种注意力稀缺源于 LLM 的架构限制。 LLM 基于 变压器架构，这使得每个令牌都能够 关注所有其他令牌 贯穿整个上下文。这会产生 n 个标记的 n² 成对关系。

随着上下文长度的增加，模型捕获这些成对关系的能力就会减弱，从而在上下文大小和注意力焦点之间产生自然的张力。此外，模型根据训练数据分布发展其注意力模式，其中较短的序列通常比较长的序列更常见。这意味着模型对上下文范围依赖关系的经验较少，并且专用参数也较少。

技术如 位置编码插值 允许模型通过使模型适应最初训练的较小上下文来处理更长的序列，尽管令牌位置理解会有所退化。这些因

这些现实意味着深思熟虑的上下文工程对于构建强大的 Agent 至关重要。

有效情境的剖析

鉴于 LLM 受到有限注意力预算的约束， 好 情境工程意味着找到 最小的 可能 一组高信号标记，可最大化某些期望结果的可能性。实施这一实践说起来容易做起来难，但在下一节中，我们概述了这一指导原则在不同背景下的实践中的含义。

系统prompt 应该非常清晰并使用简单、直接的语言来表达想法 正确的高度 对于 Agent。正确的高度是两种常见故障模式之间的金发姑娘区。在一种极端情况下，我们看到工程师在 prompt 中硬编码复杂、脆弱的逻辑，以得出精确的 Agent 行为。随着时间的推移，这种方法会造成脆弱性并增加维护复杂性。在另一个极端，工程师有时会提供模糊的高级指导，无法为 LLM 提供所需输出的具体信号，或者错误地假设共享上下文。最佳高度达到了平衡：足够具体，可以有效地指导行为，但又足够灵活，可以为模型提供强大的启发式方法来指导行为。

我们建议将 prompt 组织成不同的部分（例如 <background_information>, <instructions>, ## Tool guidance, ## Output description等）并使用 XML 标记或 Markdown 标题等技术来描述这些部分，尽管随着模型变得更加强大，prompt 的精确格式可能变得不那么重要。

无论您决定如何构建系统 prompt，您都应该努力获得完全概述您的预期行为的最小信息集。 （请注意，最小并不一定意味着短；您仍然需要预先为 Agent 提供足够的信息，以确保其遵循所需的行为。）最好首先使用可用的最佳模型测试最小 prompt，以了解它在您的任务中的执行情况，然后添加明确的说明和示例，以根据初始测试期间发现的故障模式来提高性能。

工具 允许 Agent 在其环境中运行，并在工作时引入新的附加上下文。由于工具定义了 Agent 与其信息/操作空间之间的契约，因此工具通过返回代币高效的信息和鼓励高效的 Agent 行为来提高效率非常重要。

在 AI Agent 的写入工具 – 带有 AI Agent，我们讨论了构建 LLM 可以很好理解并且功能重叠最小的工具。与精心设计的代码库的功能类似，工具应该是独立的，对错误具有鲁棒性，并且对其预期用途非常清晰。输入参数同样应该是描述性的、明确的，并发挥模型的固有优势。

我们看到的最常见的故障模式之一是臃肿的工具集，它们涵盖了太多的功能或导致关于使用哪个工具的决策点不明确。如果人类工程师不能明确地说出在给定情况下应该使用哪种工具，那么 AI Agent 就不能指望做得更好。正如我们稍后将讨论的，为 Agent 策划一套最小可行的工具还可以在长时间交互中实现更可靠的上下文维护和修剪。

提供示例（也称为少样本 prompting）是我们继续强烈建议的众所周知的最佳实践。然而，团队经常会将一系列边缘情况放入 prompt 中，试图阐明 LLM 针对特定任务应遵循的每条可能规则。我们不推荐这样做。相反，我们建议努力策划一组多样化的规范示例，以有效地描述 Agent 的预期行为。对于 LLM，示例是价值一千个字的“图片”。

我们对上下文不同组成部分的总体指导（系统 prompt, 工具, 例子, 消息历史记录等）的目的是要深思熟虑并保持上下文信息丰富但又紧凑。现在让我们深入研究在运行时动态检索上下文。

上下文 retrieval 和 Agent 搜索

在 建筑有效 AI Agent，我们强调了基于 LLM 的工作流程和 Agent 之间的差异。自从我们写那篇文章以来，我们就倾向于 简单的定义 对于 Agent：LLM 在循环中自主使用工具。

与我们的客户一起工作，我们看到该领域正在向这个简单的范式靠拢。随着底层模型的能力变得更强，Agent 的自主水平可以扩展：更智能的模型允许 Agent 独立导航细微的问题空间并从错误中恢复。

我们现在看到工程师对 Agent 设计环境的思考方式发生了转变。如今，许多 AI 原生应用程序采用某种形式的基于嵌入的预推理时间 retrieval 来呈现重要上下文，供 Agent 进行推理。随着该领域转向更多的 Agent 方法，我们越来越多地看到团队通过“及时”上下文策略来增强这些 retrieval 系统。

采用“及时”方法构建的 Agent 不是预先预处理所有相关数据，而是维护轻量级标识符（文件路径、存储的查询、Web 链接等），并使用这些引用在运行时使用工具将数据动态加载到上下文中。 Anthropic的Agent编码解决方案 Claude Code 使用这种方法对大型数据库执行复杂的数据分析。该模型可以编写有针对性的查询、存储结果，并利用 head 和 tail 等 Bash 命令来分析大量数据，而无需将完整的数据对象加载到上下文中。这种方法反映了人类的认知：我们通常不会记住整个信息库，而是引入外部组织和索引系统（例如文件系统、收件箱和书签）来按需检索相关信息。

除了存储效率之外，这些引用的元数据还提供了一种有效细化行为的机制，无论是明确提供的还是直观的。对于在文件系统中运行的 Agent，存在名为 test_utils.py 在一个 tests 文件夹意味着与位于以下位置的同名文件的用途不同 src/core_logic/ 文件夹层次结构、命名约定和时间戳都提供了重要信号，帮助人类和 Agent 了解如何以及何时使用信息。

让 Agent 自主导航和检索数据还可以实现渐进式披露，换句话说，允许 Agent 通过探索逐步发现相关上下文。每次交互都会产生上下文，为下一个决策提供信息：文件大小表明复杂性；命名约定暗示目的；时间戳可以作为相关性的Agent。Agent可以逐层组合理解，仅保留工作记忆中必要的内容，并利用笔记策略来获得额外的持久性。这种自我管理的上下文窗口使 Agent 专注于相关子集，而不是淹没在详尽但可能不相关的信息中。

当然，这是一个权衡：运行时探索比检索预先计算的数据慢。不仅如此，还需要固执己见和深思熟虑的工程，以确保 LLM 拥有正确的工具和启发法来有效地导航其信息环境。如果没有适当的指导，Agent 可能会因滥用工具、追逐死胡同或无法识别关键信息而浪费上下文。

在某些设置中，最有效的 Agent 可能会采用混合策略，预先检索一些数据以提高速度，并自行决定进一步进行自主探索。 “正确”自主级别的决策边界取决于任务。 Claude Code 是采用以下混合模型的 Agent： CLAUDE.md 文件被天真地预先放入上下文中，而像 glob 和 grep 这样的原语允许它导航其环境并及时检索文件，有效地绕过过时的索引和复杂的语法树的问题。

混合策略可能更适合动态内容较少的环境，例如法律或财务工作。随着模型能力的提高，Agent 设计将趋向于让智能模型智能地行动，逐渐减少人工管理。鉴于该领域的快速进展，“做最简单、有效的事情”可能仍然是我们对在 Claude 之上构建 Agent 的团队的最佳建议。

长期任务的上下文工程

长视野任务要求 Agent 在令牌计数超过 LLM 上下文窗口的操作序列中保持连贯性、上下文和目标导向的行为。对于需要持续工作数十分钟到多个小时的任务，例如大型代码库迁移或综合研究项目，Agent 需要专门的技术来解决上下文窗口大小限制。

等待更大的上下文窗口似乎是一个显而易见的策略。但在可预见的未来，所有大小的上下文窗口都可能会受到上下文污染和信息相关性问题的影响——至少在需要最强 Agent 性能的情况下是如此。为了使 Agent 能够在较长的时间范围内有效工作，我们开发了一些直接解决这些上下文污染约束的技术：压缩、结构化笔记和多 Agent 架构。

压实

压缩是在接近上下文窗口限制的情况下进行对话、总结其内容并使用摘要重新启动新的上下文窗口的做法。压缩通常是上下文工程中的第一个杠杆，以推动更好的长期一致性。压缩的核心是以高保真方式提取上下文窗口的内容，使 Agent 能够以最小的性能下降继续运行。

例如，在 Claude Code 中，我们通过将消息历史记录传递给模型来总结和压缩最关键的细节来实现这一点。该模型保留了架构决策、未解决的错误和实现细节，同时丢弃了冗余的工具输出或消息。然后，Agent 可以继续使用此压缩上下文以及五个最近访问的文件。用户可以获得连续性，而不必担心上下文窗口的限制。

压缩的艺术在于选择保留什么和丢弃什么，因为过于激进的压缩可能会导致微妙但关键的上下文的丢失，而这些上下文的重要性只有在以后才会变得明显。对于实施压实系统的工程师，我们建议在复杂的 Agent 迹线上仔细调整 prompt。首先最大限度地提高召回率，以确保您的压缩 prompt 从跟踪中捕获每条相关信息，然后进行迭代，通过消除多余的内容来提高精度。

一个容易悬而未决的多余内容的例子是清除工具调用和结果——一旦在消息历史记录的深处调用了一个工具，为什么 Agent 需要再次查看原始结果？最安全、最轻触的压实形式之一是工具结果清除，最近作为 Claude Developer Platform 上的功能.

结构化笔记

结构化笔记记录或 Agent 内存是一种技术，其中 Agent 定期将笔记写入上下文窗口之外的内存中。这些注释稍后会被拉回到上下文窗口中。

此策略以最小的开销提供持久内存。就像 Claude Code 创建待办事项列表，或自定义 Agent 维护 NOTES.md 文件一样，这种简单的模式允许 Agent 跟踪复杂任务的进度，维护关键上下文和依赖关系，否则这些上下文和依赖关系可能会在数十个工具调用中丢失。

Claude 玩神奇宝贝 演示内存如何在非编码域中转换 Agent 功能。 Agent 在数千个游戏步骤中保持精确的记录，跟踪目标，例如“在我在 1 号路线中训练我的神奇宝贝的最后 1,234 步中，皮卡丘已经提升了 8 级，朝着 10 级的目标迈进。”没有任何关于记忆结构的prompting，它会开发探索区域的地图，记住它已解锁的关键成就，并维护战斗策略的战略记录，帮助它了解哪些攻击最适合不同的对手。

上下文重置后，Agent 会读取自己的笔记并继续进行数小时的训练序列或地下城探索。汇总步骤之间的这种一致性可以实现长期策略，而如果仅将所有信息保留在 LLM 的上下文窗口中，这是不可能实现的。

作为我们的一部分 Sonnet 4.5发布，我们发布了 一个记忆工具 Claude Developer Platform 的公开测试版使通过基于文件的系统在上下文窗口之外存储和查阅信息变得更加容易。这使得 Agent 能够随着时间的推移建立知识库，跨会话维护项目状态，并参考以前的工作，而无需将所有内容都放在上下文中。

Agent 子架构

Sub-Agent 架构提供了另一种绕过上下文限制的方法。专门的子 Agent 可以使用干净的上下文窗口处理重点任务，而不是用一个 Agent 尝试维护整个项目的状态。主Agent与高层计划协调，而子Agent则执行深入的技术工作或使用工具查找相关信息。每个 subAgent 可能会使用数万个或更多的令牌进行广泛的探索，但仅返回其工作的浓缩、提炼摘要（通常为 1,000-2,000 个令牌）。

这种方法实现了清晰的关注点分离——详细的搜索上下文在子 Agent 中保持隔离，而主导 Agent 则专注于综合和分析结果。这种模式在 我们如何构建多 Agent 研究系统，在复杂的研究任务上表现出比单个 Agent 系统有显着的改进。

这些方法之间的选择取决于任务特征。例如：

  • 压缩可以维持需要大量来回的任务的对话流程；
  • 记笔记非常适合具有明确里程碑的迭代开发；
  • 多 Agent 架构可处理复杂的研究和分析，其中并行探索会带来好处。

即使模型不断改进，在扩展交互中保持一致性的挑战仍然是构建更有效的 Agent 的核心。

结论

上下文工程代表了我们如何使用 LLM 进行构建的根本转变。随着模型变得更加强大，面临的挑战不仅仅是制作完美的 prompt，而是在每一步中精心策划哪些信息进入模型有限的注意力预算。无论您是为长期任务实施压缩、设计令牌高效工具，还是使 Agent 能够及时探索其环境，指导原则都是相同的：找到最小的高信号令牌集，最大限度地提高您期望结果的可能性。

我们概述的技术将随着模型的改进而不断发展。我们已经看到，更智能的模型需要更少的规范工程，从而使 Agent 能够以更大的自主权运行。但即使随着能力的扩展，将上下文视为宝贵的、有限的资源仍然是构建可靠、有效的 Agent 的核心。

立即开始在 Claude Developer Platform 中进行上下文工程，并通过我们的网站获取有用的提示和最佳实践 内存和上下文管理 食谱。
